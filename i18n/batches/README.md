# Gemini Batch API ジョブ台帳

ローカルの `docs:ja:translate` が送信したジョブのID、翻訳対象のスナップショット、
翻訳条件と取得済み結果を `<UUID>.json` に保存します。APIキーは保存しません。
`.json` と一時ファイルは通常のGitコミットから除外しています。

CIではこのディレクトリを専用ブランチ **`translation-batch-state`** に保存します。
デフォルトブランチや翻訳PRとは独立しているため、未完了ジョブのPRをマージする必要はありません。
台帳は次の実行で復元され、同じジョブへ問い合わせます。このブランチは削除しないでください。

- `pending`：Google側で処理中。再送せず `docs:ja:collect` で確認。
- `complete`：取得完了。正常なリクエストだけを翻訳JSONへ反映。
- `failed`：ジョブ失敗・期限切れ、または明確に拒否された送信。
- `submitting` / `uncertain`：送信結果が不明。自動再送はしません。

`uncertain` かつ `name` がない場合は、Google側のバッチ一覧で表示名
`trilium-ja-<UUID>` を確認してください。作成済みなら台帳の `name` に `batches/...` を設定し、
`phase` を `pending` にして保存してから取得を再開します。
未作成と確認できた場合だけ `phase: "failed"` に変更して再送できます。
CIの場合は `translation-batch-state` ブランチ上の台帳を修正してください。
ジョブ作成は冪等ではないため、不明な状態の台帳を削除して再実行しないでください。

完了結果は再適用可能です。原文ハッシュ・見出し文脈・モデル・プロンプト・用語集が一致する
現在の翻訳単位だけに適用し、人手修正は上書きしません。
複数のCI実行で同じ結果を読み込んでも、APIへ再送したり使用量を重複記録したりしません。

台帳の`requests[].error`は個別失敗を表します。正常結果は保存済みのまま、次の手動翻訳で
未完了単位を送れます。CIの定期取得は失敗単位の再送も行いません。

### 完了済みバッチの検証失敗を調査する

`complete` でも翻訳結果を検証できず、PRが作成されない場合があります。
`diagnostics` に返答の位置、照合できたリクエストキー、検証失敗理由を記録します。
APIキー・SDKの例外全文・モデルの返答本文は診断ログに出力しません。
検証に失敗した返答の生成テキストは `rejectedResponses` に保存します。
これは翻訳ドキュメントの本文です。HTTPヘッダーやAPIキーは保存しません。
専用ブランチとartifactにも含まれるので、再取得後は保存データからオフラインで調査できます。

保存した既存バッチを再取得するには、台帳を復元して原文をビルドした後に実行します。

```sh
pnpm docs:ja:collect --recheck-completed
```

GitHub Actionsでは **翻訳結果を回収** で `recheck_completed` をオンにします。
欠けた結果がある完了済みバッチだけを再取得し、翻訳の新規送信は行いません。
正常な翻訳結果と人手修正は維持します。Gemini側の保存期間が過ぎている場合は
再取得できない可能性があるため、台帳を削除せず取得エラーを確認してください。

### 出力形式

新規依頼では各inline requestの `config.responseMimeType` と
`config.responseSchema` で構造化出力を指定します。
新規依頼には `format: "text-slots-v1"` を記録します。`translations` は
`{ "翻訳単位ID": { "テキスト枠ID": "訳文" } }` という入れ子のオブジェクトです。
単位ID・テキスト枠IDをスキーマの `properties` と `required` に列挙します。
保護マーカーは生成AIに渡さず、原文のマーカー間にあるテキストだけを渡します。
文全体と見出しの文脈も渡し、固定された枠に日本語を分配するよう指示します。
元々空の位置も枠に含め、コードなどの後ろに日本語の述語や助詞を補えるようにします。
枠の順序、リンク、コード、書式はプログラム側で復元し、従来の文字列形式で翻訳JSONへ保存します。
返答の項目順には依存せず、件数・ID・枠の形式・復元後のマーカーをローカルでも検証します。
1リクエストは最大16単位・原文約1万文字に加え、テキスト枠96個を目安に分割し、スキーマの複雑さを抑えます。

共通の文体・用語指示と翻訳メモリの条件は維持し、出力規約だけをプロトコルの版で区別します。
既存の正常な訳文は再翻訳不要です。`format` のない処理中バッチは旧形式のまま取得します。
実行サマリーのバッチ表にも「固定テキスト枠」または「従来のマーカー形式」を表示します。
過去の正常な `{id, translation}` 配列も読み込めますが、IDのない文字列配列は
順番が入れ替わる実例があるため、推測で割り当てず検証エラーとして保存します。

構造化出力の変更後は、まず `page_id=s3YCWHBfmYuM`、`limit=3`、
**翻訳バッチを送信** で少量を新規依頼し、
定期回収または **翻訳結果を回収** の手動実行でPRが作られることを確認してください。
これは既存バッチの再取得とは異なり、新しい有料の翻訳依頼です。
SDK経由でスキーマが送信されることは自動テストしていますが、実際のモデルから
スキーマどおり返ることは、この実サービスでの確認が必要です。

### 部分単位の検証と保存済み返答の回収

JSONの形・件数・IDの照合はリクエスト全体で検証します。その後、訳文と保護マーカーは
単位ごとに検証し、正常な部分だけを `requests[].result.translations` に保存します。
不正な部分は `requests[].unitErrors` に単位IDと理由を記録し、原文のまま残します。
正常な兄弟単位を巻き添えにせず、次回の新規依頼では未翻訳の部分だけが対象になります。

以前にリクエスト全体を拒否した返答も、`rejectedResponses` が残っていれば通常の
`docs:ja:collect` でオフライン再検証します。正常な部分を回収するための再送・再取得は不要です。
`plan` も保存済みの正常部分を考慮するので、新規送信前に重複課金を避けられます。
原文・文脈・翻訳条件の一致と人手修正の保護は従来どおりです。

GitHub Actionsでは **翻訳結果を回収** で `recheck_completed` をオフにして実行します。
未完了のバッチがあれば状態を照会しますが、新しい翻訳は送信しません。
不正な部分が残る回収はワークフローがエラーになっても、正常部分のPRを作成します。
マーカーの順序変更・欠落などは推測で補正せず、未翻訳部分として別途扱います。

### 実行サマリーと詳細な進捗

GitHub Actionsは翻訳ステップが失敗した場合も集計し、実行画面の **Summary** に
「翻訳の状況」を表示します。翻訳反映済み・未解決の失敗・処理中・送信結果不明などを
部分数で示し、失敗理由と対象ページも表示します。

全体の失敗数は現在の原文・文脈・翻訳条件が一致する単位を数え、再試行の重複、
すでに成功した部分、再試行中の部分は失敗へ重ねて数えません。
バッチ別の表は保存済み結果を含む試行ごとの件数なので、合計しないでください。
取得結果があっても途中で処理が停止して翻訳JSONに反映されていない部分は別枠で示します。

PR本文にも同じ集計を付けます。全ページの集計と失敗単位IDは
`translation-memory-...` artifact内の `.generated/translation-status/status.json`、
読みやすい版は `status.md` に保存します。これらは後続のサイト再ビルドで消えません。
APIキーや返答本文をレポートに含めません。

ローカルやDevtronでは、原文スナップショットを用意した後に次を実行できます。

```sh
pnpm docs:ja:status
```

このコマンドはAPIを呼び出さず、手元の翻訳JSONと台帳を集計します。
台帳を復元していない場合は、処理中・失敗を判別できない未翻訳部分を
「対応する台帳なし」と表示します。
